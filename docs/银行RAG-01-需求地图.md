# 银行内部 RAG 知识库 —— 业务需求地图

> 定位：给**行内员工**用的"制度 / 业务知识副驾"，不是给客户的 chatbot。
> 产品边界：只提供**辅助决策的信息**，不做决策。所有高置信输出带"AI 生成，仅供参考"。

## 1. 先看差异：银行 RAG 与互联网 RAG 的六条本质不同

这六条决定了后面**所有**技术选型，先讲业务约束再讲技术，是这个项目最值钱的部分。

| # | 维度 | 互联网 RAG | 银行内部 RAG | 推导出的技术硬约束 |
|---|---|---|---|---|
| 1 | 权限粒度 | "能不能用这个功能" | 同一份制度，风险条线看到授信细则，柜员只看到操作规程 | 权限必须**下沉到 chunk 级 metadata**，在向量库检索时过滤，不能"查完再筛" |
| 2 | 时效 | 差不多就行 | 制度废止/替换极频繁，引用已废止条款 = 事故 | 文档必须有**生效/失效日期 + 版本号**，检索按"业务发生日"过滤 |
| 3 | 答错的成本 | 用户体验下降 | 误导操作 → 资金损失 → 监管问责 | **拒答优先**：检索不到就明说不知道，禁止模型用自身知识兜底 |
| 4 | 可追溯 | 有引用更好 | 法定要求：结论必须能指回条款原文 | **引用必须能对齐到 chunk 原文片段**，对齐失败即降级为拒答 |
| 5 | 数据边界 | 无所谓 | 客户信息、账户、征信绝不能出域 | 模型 / embedding / rerank **全部私有化**；连可观测平台都不能用 SaaS |
| 6 | 输出性质 | 直接给答案 | 只是**辅助**，高风险场景要人工终审 | 免责声明 + 高风险话题状态机 + 全量不可篡改审计 |

## 2. 八类真实场景

"真实痛点"一列写的是行内人会说出来的原话——需求从这些话里来，不是从技术名词来。

| 优先级 | 场景 | 真实痛点 | 关键技术要求 | 风险 |
|---|---|---|---|---|
| P0 | **规章制度问答** | "这业务到底按哪份文件办？新旧版本混着，我每次都得问老同事" | 版本时效、条文级引用、废止自动下线、跨制度多跳引用 | 中 |
| P0 | **运维 / 研发知识** | "这个报错上次怎么解的？工单翻不到了" | 代码脱敏、密级联动（本仓库已开） | 低 |
| P1 | **柜面 / 坐席实时辅助** | "跨行转账手续费多少？几天到账？" 客户在电话那头等着 | P95 < 2s、**实时数据必须走工具不能进知识库**、兜底转人工 | 中高（对外） |
| P1 | **信贷 / 授信尽调** | 财报、流水、征信、合同堆一桌，写报告靠手抄 | 扫描件 OCR、表格理解、结构化抽取、强制人工复核 | 高 |
| P1 | **合规 / 反洗钱** | "这笔可疑交易报告怎么写？" | 名单实时查询、极强审计、不可篡改留痕 | 极高 |
| P1 | **员工培训 / 考试** | 新人上手慢，培训材料常年不更新 | 低风险，**适合作为冷启动场景** | 低 |
| P2 | **投研 / 理财产品** | 产品说明书、风险揭示散落 | 红线：不得构成投资建议（持牌），强制风险揭示 | 高 |
| P2 | **监管报送 / 审计** | 报送口径年年变，历史口径查不到 | 口径版本化、可回溯到报送时点 | 高 |

**选择建议**：从 **P0 制度问答 + 培训问答**冷启动。制度问答需求最刚性、数据最容易拿、风险可控；培训场景可以拿来跑通评测闭环。

## 3. 三个场景深挖

### 3.1 规章制度问答（主战场）

一次完整问答的数据流，每一环都对应一个技术点：

```
问题
 ├─ 1. 多轮指代消解      "那它呢？" → 补全为自包含问题
 ├─ 2. 抽取过滤条件      业务日期 / 业务条线 / 机构层级
 ├─ 3. 混合检索          BM25 抓文号条款号 + 向量抓口语语义 → RRF 融合
 ├─ 4. 精排              cross-encoder 重排 top50 → top5
 ├─ 5. 权限 + 时效过滤    kb_id / doc_level / org_codes / 生效区间（下推到库）
 ├─ 6. Small-to-Big      命中"条" → 取回所属"章"做上下文
 ├─ 7. 生成              强制引用 [1][2]，仅基于授权资料
 ├─ 8. 引用对齐校验      引用必须能落到 chunk 原文片段，否则降级拒答
 └─ 9. 输出              免责声明 + AI 标识 → 审计落库
```

**两个最容易被忽略、又最致命的点：**

1. **时效过滤**。检索时按 `effective_from <= 业务日期 <= effective_to` 过滤；命中已废止文档时要**显式提示**"该制度已于 X 年 X 月废止，替代文件为 Y"。绝大多数 RAG demo 都没做这件事，而在银行这是事故级缺陷。
2. **多跳引用**。"根据《XX 办法》第十八条"——A 制度指向 B 制度，向量检索只会召回 A，答案就断了。这需要 §1.6 的轻量图谱做一跳展开。

### 3.2 柜面 / 坐席实时辅助

- **核心洞察（面试必讲）**：**费率、利率、汇率是"事实型实时数据"，不属于知识，绝不能进向量库**。
  RAG 管"**怎么办**"（制度、流程、话术），Function Calling 管"**是多少**"（当前值）。
  这是 function calling 在银行最自然的落点——如果只能讲一个技术亮点，讲这个。
- **延迟预算拆解**（目标 P95 < 2s，非常紧）：

  | 环节 | 预算 |
  |---|---|
  | 输入 / ASR | 0 ms（已有） |
  | 向量 + BM25 检索 | ~300 ms |
  | Rerank | ~200 ms |
  | 工具调用（查费率） | ~200 ms |
  | 生成首 token | ~800 ms |
  | **合计** | **~1.5 s（余量很小）** |

  → 结论：坐席场景**必须**上小模型 + 语义缓存 + 减少 rerank 候选数，"用最强模型"在这里是错误答案。

### 3.3 信贷 / 授信尽调

- 输入是 PDF 且**大量是扫描件** → OCR 是必需项。
- 财务报表表格**不能只当文本**：要么结构化抽取成 JSON，要么走 SQL/计算工具。
- 输出是**初稿**，必须带"未经人工复核不得对外"，并进入双人签核流程。
- 适合用 Agentic 流程（多步、可慢），与坐席场景形成鲜明对比——**同一个技术栈，不同场景不同编排策略**。

## 4. 把需求翻译成可测的数字（非功能指标）

银行评审会只认数字。建议目标：

| 指标 | 目标 | 为什么是它 |
|---|---|---|
| 检索召回率 @10 | ≥ 90% | 召回不到，后面全废 |
| **引用准确率**（引用真能支撑结论） | ≥ 95% | 银行的核心指标，低于此不可用 |
| 正确拒答率 | ≥ 95% | "拒答优先"策略的前提 |
| 幻觉率（无证据断言） | ≤ 1% | 上生产红线 |
| P95 端到端延迟 | 制度问答 < 5s；坐席 < 2s | 场景决定 |
| **权限越权次数** | **0（事故级）** | 必须有专门的红队越权测试用例 |

## 5. 本仓库现状盘点（对照差距）

**已经有的（比大多数 demo 强的地方）**：

- Spring AI 1.0.0 + PgVector + OpenAI 兼容协议
- **权限三把锁**：`PermissionAdvisor`（会话快照 + auth_version 熔断 + 配额）→ `RetrievalAdvisor`（metadata filter **下推向量库** + 检索后 fail-closed 二次门禁）
- `CodeRedactor` 代码脱敏 + 密级联动（≥5 级才放行代码）
- 摄取链路：`MarkdownChunker` + `DocMetadataParser` + `IngestManifestLoader`
- `spring-ai-starter-mcp-client` 依赖已引入（配置暂注释）
- 会话表设计文档（含审计表规划）

**缺口（按优先级排序）**：

| # | 缺口 | 对应本文档 |
|---|---|---|
| 1 | 检索只有纯向量，无 BM25 / hybrid / rerank | §1.1 §1.2 |
| 2 | ~~embedding 走外部 API~~ —— 练习环境有意选择，**不是缺陷**，见选型文档 §一 | — |
| 3 | `DocMetadata` **已有** `effectiveFrom`/`effectiveUntil`/`version` 且解析正常，但**没写进 chunk metadata、检索侧完全没用** —— 时效字段目前形同虚设 | §3.1 |
| 4 | 无引用归因、无拒答判定逻辑 | §3.1 |
| 5 | 无 function calling 工具层 | 技术亮点 §二 |
| 6 | 审计表（`rag_assistant_audit_log`）已规划未落地 | 技术亮点 §3.3 |
| 7 | 无评测集，无法证明"准确率 92%" | 技术亮点 §3.4 |
