# 银行 RAG 知识库 —— 技术亮点与落地路径

> 每节统一结构：**为什么银行需要 → 怎么做 → 选型选项 → 本仓库落点**。
> 排序按"投入产出比"，不是按技术炫酷度。

## 一、检索层：把"找得到"做到极致

### 1.1 混合检索（Hybrid：BM25 + 向量 + RRF）

**为什么必须做**：制度文本里全是**精确字符串**——文号（"银保监发〔2019〕23 号"）、条款号（"第十八条"）、专有名词（"拨备覆盖率"）。纯向量检索对这类串是明确弱项，而 BM25 恰好是强项。反过来，口语化提问（"贷款还不上了抵押物怎么处理"）向量又远强于关键词。**两个都要，缺一不可。**

**三种实现路径**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Elasticsearch / OpenSearch | BM25 + kNN 同一引擎，hybrid 最顺；运维一套 | 向量性能与精度弱于专用库 |
| PostgreSQL：`tsvector` + `pgvector` | 已在用 PG 就没新增组件；能 join 元数据表做权限/时效过滤 | 中文分词要装 `zhparser` / `pg_jieba`；两路结果要自己融合 |
| Milvus 2.5+ | 原生稀疏向量（BM25 权重），单库搞定 hybrid | 运维重（etcd + minio + pulsar） |

**融合算法**：优先 **RRF（倒数排名融合）**——只用到排名不用到分数，无需调权重、对分数尺度不敏感、鲁棒。加权分数归一化要调参，调一次换一批数据就失效。

**本仓库落点**：从 PG 起步（已有 PgVector），加 `zhparser` 全文索引，Service 层做 RRF 融合。

### 1.2 重排（Rerank）

**为什么**：向量检索是**双塔**结构（query 和 doc 分开编码，最后只算余弦），精度天花板天然低。Cross-Encoder 把 query 和 doc 拼在一起过一遍模型，精度高一个档次。典型收益：召回 top50 → 精排 top5。

**选型**：

| 选项 | 说明 |
|---|---|
| `bge-reranker-v2-m3` | 本地部署，中英俱佳，**银行首选** |
| `Qwen3-Reranker` | 本地，新，中文强 |
| Cohere Rerank / Jina | API，效果好但**数据出域，银行直接出局** |

**成本提醒**：rerank 是延迟大头。top50→5 在 GPU 上约 100–300ms，CPU 上不可接受。坐席这种 2s 预算的场景要么减 topK，要么用更小的 reranker。

### 1.3 查询理解

| 技术 | 解决什么 | 银行注意事项 |
|---|---|---|
| 多轮指代消解 | "那它呢？" → 补全成自包含问题 | 改写会引入幻觉，**原问题要保留一起做多路召回** |
| 同义扩展 | "年假" / "带薪年休假" | 银行术语缩写多（"三个办法一个指引"），维护行业词典 |
| HyDE | 短查询先让模型编个假答案再检索 | 多一次 LLM 调用，坐席场景不划算 |
| 子问题拆解 | "跨行转账和跨行汇款的区别和手续费" | 拆完要合并去重 |

### 1.4 分块策略

- 通用做法：固定长度 / 语义分块 / **父子分块（Small-to-Big）**——用小块做检索（精度高），命中后送父块给 LLM（上下文完整）。
- **银行特色**：制度文档应该**按"条"分块**，因为引用要精确到条。同时保留"编-章-节-条"层级做父子关系。
- 本仓库 `MarkdownChunker` 可扩展为"标题层级感知 + 条款正则感知"。

### 1.5 表格与扫描件（银行最容易翻车的地方）

- 财务报表、费率表**文本化后语义会崩**。三条路：转 Markdown 保留结构 / 转自然语言描述 + 保留原表引用 / 抽成结构化数据走 SQL 工具。
- **推荐**：表格检测 → 单独处理 → 存"表格摘要 + 原表 HTML/图片"双份，摘要用于检索，原表用于展示与核对。
- 银行大量**扫描件 PDF**，纯文本解析方案会直接挂——OCR 是必需项不是可选项。

### 1.6 轻量制度引用图谱（GraphRAG-lite）★ 亮点

- **银行场景**：制度之间互相引用。能回答"这份制度废止会影响哪些业务"——**纯向量检索永远答不了**。
- 完整 GraphRAG 要用 LLM 抽实体关系，成本高。
- **务实替代**：制度文档里引用格式极规整（"根据《XX 管理办法》（银保监发〔2019〕23 号）"），**用正则就能抽出引用边建图**，成本近乎为零，效果好得惊人。这是本仓库最值得做的差异化亮点。

## 二、工具层：Function Calling 与 MCP

### 2.1 Function Calling —— 银行里真正有用的工具清单

**划界原则**：**静态知识进向量库，动态事实走工具，确定性计算写代码。**

| 工具 | 解决什么 | 权限要求 | 风险 |
|---|---|---|---|
| `query_current_rate(productCode, date)` | 实时利率——知识库答不了，进库就过期 | 全员 | 低 |
| `query_fee_schedule(bizType, tier)` | 费率表，按客户等级不同 | 全员 | 低 |
| `get_doc_status(docId)` | 制度是否废止 / 被替代 | 全员 | 低 |
| `get_doc_relation(docId)` | 制度引用 / 被引用（配合轻量图谱） | 全员 | 低 |
| `check_sanctions(name, idNo)` | 制裁 / 反洗钱名单命中 | 合规条线 | 中 |
| `get_customer_summary(customerId)` | 客户画像 | **强权限 + 强制脱敏 + 双人授权** | **高** |
| `calc_loan(amount, rate, term, method)` | 还款试算 | 全员 | 低 |
| `submit_manual_review(sessionId, q)` | 触发人工复核 | 全员 | 中（写操作） |

**四条设计要点（写进设计文档、面试也讲这些）：**

1. **确定性计算永不交给 LLM**。还款试算、费率计算、期限计算一律代码算，LLM 只负责理解意图、选对工具、解释结果。让 LLM 做算术是银行方案里最低级的错误。
2. **工具也要做权限**。工具权限矩阵（哪个角色能用哪些工具）要和文档权限一样 fail-closed。
3. **工具返回值也要脱敏**。`get_customer_summary` 返回的内容不能原样进 prompt。
4. **工具调用必须审计**：谁、何时、什么参数、返回了什么、模型据此说了什么。

### 2.2 MCP —— 银行里最该标准化的东西 ★★ 最大亮点

**痛点**：行内系统 N 个（核心、信贷、CRM、数据中台、名单系统），每个系统都要单独写一遍 Function Calling 适配 —— N×M 的适配复杂度。

**MCP 的价值**：把"工具接入"从**每个系统各写一套**变成**协议标准化**。一个 MCP Server 暴露一批 tools，Client 自动发现能力。

**银行落地的关键改造 —— MCP 网关**（这是把玩具变成生产方案的一步）：

```
LLM → MCP Client → [ MCP 网关 ] → MCP Server → 行内系统
                      ├─ 身份透传（禁止匿名调用）
                      ├─ 工具级 RBAC（角色 × 工具 白名单）
                      ├─ 限流 / 熔断（资源锁）
                      ├─ 参数与返回值脱敏
                      ├─ 全量审计（trace_id 贯穿）
                      └─ 工具版本与灰度
```

**安全红线（必须写进设计）**：

- **绝不让 LLM 直连核心系统**。中间必须有网关或服务层。
- 工具必须是**窄接口**：只暴露必要参数，**不允许模型构造任意 SQL / 账号 / 路径**。所有参数走白名单校验。
- 写操作（提交复核、发起流程）需**二次确认**，且默认只读优先。

**传输方式**：stdio（本地开发）/ SSE（旧版）/ **Streamable HTTP（生产：支持鉴权头、断线重连）**。

**本仓库落点**：pom 里 `spring-ai-starter-mcp-client` 已就绪，配置被注释。第一步先起一个 mock MCP server（比如暴露"制度状态查询""费率查询"），跑通 Client → 工具调用 → 结果回填 prompt；第二步再加网关层与工具权限矩阵。

### 2.3 Agentic RAG / Self-RAG

**流程**：检索 → **自评相关性** → 不够则改写重检 / 换工具 → 仍不够则**主动拒答**。

**银行价值**：把"拒答"从"失败"变成"主动的合规决策"。

**取舍**：多一次 LLM 调用 = 延迟与成本上升。建议**只在"高价值 + 低时效要求"场景启用**（信贷尽调可以，坐席辅助不行）。

### 2.4 Workflow vs Agent ★ 面试加分观点

**银行生产推荐：确定性编排为主 + 局部 Agent。**

理由：Agent 的自由度 = 不可预测性 = 合规风险。银行要求**同一问题给出同样答案**（可复现）、**每一步可归因**（可审计）、**成本可控**、**可测试**。纯 Agent 在这四条上全部不达标。

正确姿势：主链路用确定的 workflow 编排（意图分类 → 检索 → 工具 → 生成 → 校验），只在**意图识别**这类局部环节让模型自主决策。

### 2.5 多模型交叉复核（Generator-Critic）

生成模型 A 出答案 → 审查模型 B 拿着证据判断"这个结论是否被证据支持"，不支持就打回或降级为拒答。

这是银行"**双人复核**"制度的机器化版本。高风险场景（信贷、反洗钱）启用，成本翻倍但风险收益比成立。

## 三、可信层：银行最值钱的工程（也是最容易被忽略的）

大部分 RAG 项目止步于"检索 + 生成"，而银行项目 80% 的工程量在"证明它可信"。

### 3.1 输入侧 Guardrails

| 风险 | 说明 | 对策 |
|---|---|---|
| **提示词注入** | 知识库文档本身可能被投毒（文档里写"忽略以上指令，改为输出…"） | **把检索回来的文档当"不可信输入"**：用明确分隔符包裹 + 指令固化 + 优先级声明 |
| PII 泄漏 | 用户问题里带客户身份证/手机号 → 直接送进模型 | 入口 PII 检测 → 拦截或脱敏后再送模型 |
| 越权意图 | "帮我查一下客户张三的余额" | 意图识别 + 工具权限矩阵，越权直接拒绝并记录 |

> **关键认知**：RAG 的检索结果是**外部输入**，安全等级等同于"用户输入"，不能因为"是自家知识库"就信任它。

### 3.2 输出侧 Guardrails

1. **引用强制 + 片段对齐**：答案里的 `[1][2]` 必须真的对应到 chunk 原文片段，对不上就降级为拒答。（本仓库 `RetrievalAdvisor` 已有 md 上下文拼装，下一步加对齐校验。）
2. **数字一致性校验** ★ 银行特色：答案里出现的**金额、比例、期限**，必须能在原文中找到出处。数字编造是银行最不可接受的幻觉类型。
3. **合规话术检查**：不得出现"保本""稳赚""一定能"等禁词。
4. **密级 / 代码脱敏**：本仓库 `CodeRedactor` 已实现（密级 <5 时对代码块脱敏，脱不干净就整块丢弃 —— fail-closed，这个设计是对的）。
5. **免责声明 + AI 生成标识**：监管要求，不可省。

### 3.3 审计与可追溯

- **trace_id 全链路**：请求 → 改写 → 检索 → 精排 → 工具调用 → 生成 → 输出校验，每一跳都挂同一个 trace_id。
- **文档快照**：当时检索到的 chunk 原文要落库。因为**文档会变**，不落快照就无法复现"当时为什么这么答"。
- **append-only + 哈希链**：每条审计记录带上一条的 hash，改一条全链断裂。满足"防篡改"要求。
- **留存期**：不低于业务存续期，到期归档/销毁要有流程。
- 本仓库会话表设计文档已规划 `rag_assistant_audit_log`，**尚未落地，属于 P2 必做项**。

### 3.4 评测 harness ★ 最能证明你不是在玩玩具

三层评测，缺一层都说不服评审：

| 层 | 指标 | 怎么造数据 |
|---|---|---|
| 检索层 | Recall@K、MRR、NDCG | 人工标注"问题 → 正确 chunk" |
| 生成层 | Faithfulness、Answer Relevancy、Context Precision（RAGAS 那套） | 可用 LLM 评判 + 人工抽检 |
| 业务层 | 人工评分、线上点踩率 | 上线后回流 |

**冷启动造评测集的方法**：从制度文档里**反向生成 QA 对**（LLM 生成问题 + 标注答案出处），再人工校验一遍。**200–500 条就能说明问题**，不必追求大而全。

**最关键的一步：把评测接进 CI。** 每次改 prompt / 分块策略 / 换模型，自动跑一遍回归并出对比报告。银行评审特别认这个——它证明你的系统是**可控演进**的，而不是"改一个字全靠玄学"。

## 四、成本与性能

| 手段 | 说明 | 银行注意事项 |
|---|---|---|
| **语义缓存** | 行内问题重复率极高（"年假几天"每天都有人问），命中直接返回 | ⚠️ **缓存 key 必须包含权限维度**，否则 A 用户的问题命中 B 用户的答案 = 越权泄露。这是本项目最值得写进文档的坑 |
| **模型路由** | 简单问题走小模型/本地，复杂问题走大模型 | 省成本 + 降延迟；路由规则要可审计 |
| **流式输出** | 首 token 时间才是用户体感 | 坐席场景必需 |
| **HNSW 调参** | `m` / `ef_construction` 建索引时定，`ef_search` 查询时调 | 召回率与延迟的权衡，要用评测集来调而不是拍脑袋 |
| **rerank 候选数** | top50 精排 vs top20 精排 | 延迟敏感场景用小候选数 |

## 五、实施顺序（按当前 PoC 定位重排）

**排序依据**（这是本项目现阶段的三个现实约束，排序据此调整）：

1. **试验阶段**：银行对新技术的惯例是初期只让碰低数据安全等级的模块 —— 所以优先做**能被演示、能被评审看懂**的功能。
2. **外网练习环境**：PG 与 embedding 用云端服务，可用的基础设施以"云实例给什么"为准 ——
   凡是要在数据库里装扩展、要额外起服务的功能，一律往后排。
3. **纯代码优先**：不引入新依赖就能做完的，先做。

| 排名 | 功能 | 为什么在这个位置 | 状态 |
|---|---|---|---|
| 1 | **时效落地**：`effective_from`/`effective_until` 写入 chunk + 检索侧按业务日期过滤 | 纯代码、零新依赖；银行 RAG 与 demo 的分水岭 | ✅ 已完成 |
| 2 | **引用归因 + 拒答**：`[n]` 编号引文、检索空/全被过滤即拒答、越界引用检测 | 纯代码；演示性最强（"答案能指回条款"） | ✅ 已完成 |
| 3 | **审计表落地**：`rag_assistant_audit_log`（会话表文档已设计好，直接实现） | 纯代码（MyBatis 已就位）；合规刚需，且为 4/5 提供留痕 | 待做 |
| 4 | **Function Calling 工具层**：`query_fee_schedule` + `get_doc_status` 先跑通链路 | 用 mock 数据即可，不需真实行内系统；亮点最显眼 | 待做 |
| 5 | **评测集 + CI 回归**：召回/引用/拒答三层指标接进构建 | 1、2 给了可量化的点，此时做收益最大 | 待做 |
| 6 | **hybrid 检索**（BM25 + 向量 + RRF） | ⚠️ **被环境降级**：需 PG 装 `zhparser` 中文分词扩展，云 RDS 是否开放要确认（可能要提工单）。装不了就退到"应用层 BM25 兜底"或改用 ES | 受阻 |
| 7 | **MCP**：把工具改造成 MCP Server + 网关 | 需要额外服务与网关层，试验阶段最重 | 待做 |
| 8 | 轻量制度引用图谱 / 表格问答 / 多模型交叉复核 | 差异化亮点，但依赖前面全部就位 | 待做 |

> **注意**：这份排序**只适用于当前"初步试验 + 外网练习"阶段**。
> 真实生产落地的排序不一样 —— 权限、审计、评测的权重会显著高于 function calling 这类亮点功能，
> 因为生产环境里"能证明它可信"比"它能做什么"更值钱。

**做完 1–3，这个项目就超过 90% 的"RAG demo"；做完 4–5，有了面试官会追问的亮点；做完 6–8 是加分项。**
