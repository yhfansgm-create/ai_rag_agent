# 银行 RAG 知识库 —— 监管约束与技术选型

> ⚠️ 说明：以下法规/标准的**编号与条款请以官方最新发布为准**，本文给出的是它们**推导出的技术方向**，
> 用于建立"监管 → 技术红线"的思维方式，而不是法律意见。
>
> 📌 **本文的定位**：这些监管要求是**选型知识**，用来建立判断力。本项目当前是**外网练习 PoC**，
> 只使用低敏感度数据（银行对新技术的惯例也是初期只让碰低安全等级模块）；
> 云端 PG 与云端 embedding 是练习阶段的**有意选择，不构成待整改缺陷**。真实部署才需要私有化。

## 一、监管约束 → 技术红线

选型不是从"哪个技术新"出发，是从"哪条监管要求会毙掉它"出发。

| 法规 / 标准 | 大致要求 | 推导出的技术红线 |
|---|---|---|
| 《生成式人工智能服务管理暂行办法》 | 面向公众的生成式服务需备案；内容标识；训练数据合法；不得生成虚假有害信息 | 输出显式标识"AI 生成"；面向行内员工可豁免部分条款，但**建议按同标准执行** |
| 《金融数据安全 数据安全分级指南》JR/T 0197 | 数据按 1–5 级分级管控 | 文档**分级入库**，权限按级控制（本仓库 `doc_level` 1–5 已对齐） |
| 《个人金融信息保护技术规范》JR/T 0171 | 个人金融信息分 C1/C2/C3 | **C3（账户、密码、密钥）绝不允许出现在 prompt、日志、向量库任何位置** |
| 《人工智能算法金融应用评价规范》JR/T 0221 | 算法需可解释、可追溯、安全性、准确性评价 | 必须做**评测集 + 可解释性 + 审计留痕**，不能"跑起来就行" |
| 网络安全等级保护 2.0 三级 | 访问控制、安全审计、数据完整性 | append-only 审计日志、传输加密、双因子 |
| 《银行保险机构信息科技外包风险监管办法》 | 外部云服务/外部模型属于外包，需评估备案 | 外部 API **必须评估**；敏感数据不出域；模型选型要过科技风险评审 |
| 互联网贷款 / 理财销售等业务办法 | 不得替代人工决策、不得误导销售 | 免责声明 + 高风险人工复核 + 话术禁词管控 |

**一句话总结红线**：*数据不出域、权限下沉、结论可溯、输出标识、留痕不可篡改、高风险人工终审。*

## 二、十道选型题（选项 / 取舍 / 推荐 / 本项目现状）

### 1. LLM 部署形态
- **A 公有云 API**（DeepSeek / 通义 / 智谱）：便宜、快、能力强；**敏感数据出域**，涉客场景直接出局。
- **B 私有化开源**（Qwen3-32B、DeepSeek 蒸馏版、GLM，vLLM 部署）：一次性 GPU 投入大，但是**唯一能过合规**的路。
- **C 混合路由**：公开制度走云、涉客数据走本地。最现实，但要先建**数据分级路由**能力。
- **D 复用行内大模型平台**：很多银行已在建，银行落地的**实际最优解**（复用算力与合规资质）。

> **推荐**：学习项目用 A 起步（本仓库现状），但**架构上留出 C 的接口**；讲银行方案时讲 B/D。

### 2. Embedding 模型 ★ 最容易被忽略的坑
- 选项：API（DashScope `text-embedding-v3`、OpenAI）vs **本地开源**（`bge-m3`、`bge-large-zh-v1.5`、`Qwen3-Embedding`、`Conan-embedding`）。
- **两个致命理由必须本地**：① embedding 请求携带**文档原文**，走 API 等于原文出域；② **换 embedding 模型要全库重灌**，迁移成本极高，必须一次选对。
- **推荐**：`bge-m3`（中文强、支持 8k 长文本、可选输出稀疏向量配合 hybrid）。

> 📌 **本项目现状**：练习阶段在外网环境，embedding 与 PG 均用云端服务，这是有意选择。
> 面试讲选型时把"为什么在真实银行里必须本地"当作知识点讲即可，**不需要对本项目发告警**。

### 3. 向量库
| 选项 | 优势 | 代价 |
|---|---|---|
| **PgVector** | 已在用 PG 则运维成本≈0；可 join 元数据表做权限/时效过滤；千万级 chunk 够用 | 超大规模 / 高并发吃力 |
| **Milvus** | 十亿级；原生稀疏向量 hybrid 好 | 运维重（etcd/minio/pulsar） |
| **Elasticsearch / OpenSearch** | BM25 + kNN 一体，hybrid 最顺 | 向量精度性能弱于专用库 |
| **Qdrant / Weaviate** | 轻量、API 优雅 | 国内信创适配少 |
| **国产信创** | 腾讯云 VectorDB、阿里 Lindorm、华为 GaussDB(vector)、openGauss | 生态与文档相对少 |

> 银行额外两个维度：**信创名录** + **行内已有运维栈**。
> **推荐**：≤1000 万 chunk 且已有 PG → PgVector（本仓库选择正确）；要 hybrid 且已有 ES → ES；有信创要求 → 国产。

### 4. 编排框架
- **Spring AI**：Java 栈，Advisor 模型清晰，行内 Java 团队友好（**本仓库选择**）。
- **LangChain4j**：Java，AI Services 抽象更好，功能更全。
- **Python 系**（LangChain / LlamaIndex）：生态最全，但行内运维与安全评审难。
- **低代码平台**（Dify / FastGPT / Coze）：PoC 极快，生产要评估**数据边界与可审计性**。
> 银行生产倾向：**自研薄编排层**（可审计、可控、可灰度）。

### 5. 重排模型
`bge-reranker-v2-m3`（本地，**推荐**）/ Cohere Rerank（API，出域❌）/ 不用（省延迟，牺牲精度）。

### 6. 文档解析
- 纯文本 PDF：Tika / PDFBox 够用。
- 扫描件：**OCR 必需**（PaddleOCR / 合合 / 百度），版面分析（MinerU、PP-StructureV3）处理双栏与表格。

### 7. MCP 传输方式
stdio（本地开发）/ SSE（旧）/ **Streamable HTTP（生产：支持鉴权头、断线重连）**。

### 8. 会话与记忆
内存（开发）/ **JDBC 落库（推荐，可审计）** / Redis（高性能，但审计要另做持久化）。

### 9. 鉴权
应用自建 session（本仓库现状）/ **OAuth2 + OIDC 对接行内 IAM（生产）** / 网关统一（API Gateway 做认证，应用做授权）。

### 10. 可观测性
**Langfuse（可自托管 ✓）** / Phoenix / 自建 OTel + Micrometer / SaaS（❌ **prompt 与原文等同业务数据，绝不能送 SaaS**）。

## 三、选型决策树（把上面十道题压缩成可执行的判断）

```
① 数据能不能出域？
   ├─ 不能（涉客 / 内部数据）→ 全私有化：本地 embedding + 本地 LLM + 本地向量库 + 自托管可观测
   └─ 能（仅公开制度）→ 可以用云 API，但仍建议私有化（一致性 + 迁移成本）
        ↓
② 规模多大？
   ├─ < 1000 万 chunk → PgVector（已有 PG）或 ES
   └─ > 1000 万 chunk → Milvus
        ↓
③ 要不要 hybrid？要 → ES / Milvus 2.5 / PG + zhparser；不要 → PgVector 足够
        ↓
④ 有没有信创要求？有 → 国产向量库 + 国产模型（Qwen / GLM / 文心）
```

**一条经验法则**：*能复用行内已有组件的方案，永远优先于"技术更先进"的方案。* 银行选型的最大成本不是 License，是**运维与安全评审**。

## 四、落地路线图（P0–P5 共六阶段，每阶段都有可演示产出）

| 阶段 | 主题 | 具体任务 | 可演示产出 |
|---|---|---|---|
| **P0** | 骨架（已完成） | 权限三把锁、摄取链路、PgVector、代码脱敏 | 会话鉴权 + 向量检索 demo |
| **P1** | 检索质量 | 文档版本/时效字段 → hybrid（+BM25/RRF）→ rerank → 引用归因 → 拒答判定 | "问制度，答案带条款引用，废止的自动提示" |
| **P2** | 工具层 | function calling（费率/利率/制度状态）+ 工具权限矩阵 + 审计表落地 | "查跨行转账手续费，走工具拿到实时值" |
| **P3** | MCP | mock MCP server → MCP 网关（鉴权/限流/脱敏/审计）+ 工具白名单 | "接入一个行内系统，零改业务代码" |
| **P4** | 可信与评测 | eval harness（召回/引用/拒答）+ CI 回归 + 语义缓存 + 模型路由 | "准确率 92%、拒答率 96%，每次改 prompt 自动回归" |
| **P5** | 差异化亮点 | 轻量制度引用图谱 + 表格问答 + 多模型交叉复核 | "问『这份制度废止影响哪些业务』能答出来" |

**P1 → P2 是性价比最高的两步**：P1 让项目从"能跑"变成"能用"，P2 引入 function calling 这个最容易被面试官注意到的亮点。

## 五、面试怎么讲（把项目讲成银行经验）

**1. 先讲约束，再讲方案。** 开场用"银行 RAG 六条本质差异"，面试官立刻知道你不是在堆技术名词。绝大多数候选人上来就讲向量库选型，格局就小了。

**2. 三个必讲的技术决策：**

- **权限下沉到向量库 metadata filter**（不是查完再筛）+ 会话权限快照 + `auth_version` TOCTOU 熔断 —— 对应"三把锁"。
- **Function Calling 划清"事实型实时数据"与"知识型静态数据"的边界**；确定性计算不交给 LLM。
- **MCP 网关：绝不让 LLM 直连核心系统**，工具窄接口 + 工具级 RBAC + 全量审计。

**3. 主动讲取舍。** 面试官最爱听"你为什么不选 X"：

- 为什么 PgVector 而不是 Milvus？→ 规模没到 + 复用行内运维栈 + 能 join 元数据表做权限过滤。
- 为什么 workflow 为主而不是纯 Agent？→ 可复现、可审计、成本可控。
- 为什么 embedding 必须本地？→ 原文出域 + 换模型要全库重灌。

**4. 讲你踩过的坑（真实感最强）：**

- **语义缓存 key 不带权限维度 → 越权泄露**。缓存命中直接返回，绕过了整个权限链路。这是个漂亮的坑。
- **换 embedding 模型要全库重灌**，且新旧向量不能混用。
- **文档废止没下线** → 助手引用过期条款，是事故级缺陷。
- **rerank 是延迟大头**，坐席 2s 预算下 top50 精排跑不动。

**5. 量化。** 没有数字的经验分享不值钱：召回率、引用准确率、拒答率、P95 延迟、单次成本。
