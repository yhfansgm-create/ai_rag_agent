# 银行 RAG —— 平台内核与场景特化：哪些能套用，哪些不能

## 一、直接回答那个问题

> 问：是不是只要实现了这一套，任意功能只是知识库不同，都可以直接往上套用？

**一半对。**

- **对的那一半：管道可以套用。** 检索怎么执行、过滤器怎么下推、审计怎么落库、拒答怎么短路、引文怎么拼装 ——
  这部分建一次，换个场景确实就是换个知识库。
- **错的那一半：语义不能套用。** 什么算"有权看"、什么算"已过期"、什么算"答对了"、什么算"必须拒绝" ——
  这部分每个场景都要重新定义，而且**恰恰是最容易出事故的地方**。

一句话原则（借操作系统设计的经典区分）：

> **机制（mechanism）可复用，策略（policy）必须重定。**

| | 内容 | 复用性 |
|---|---|---|
| **机制** | 怎么检索、怎么下推过滤、怎么短路拒答、怎么拼引用、怎么留痕 | 一套，建一次 |
| **策略** | 谁能看什么、什么时间有效、答到什么程度算可信、什么情况必须转人工 | 每场景一套 |

## 二、先承认一个混淆：那张表排的是"学习路径"

你感觉"联系不到具体功能"，是因为它本来就不是按功能排的：

| | 学习路径（我上次那张表） | 产品路线图 |
|---|---|---|
| 单位 | **能力**（数字校验、引用图谱、工具层） | **场景**（制度问答、坐席辅助、信贷尽调） |
| 排序依据 | 亮点 + 难度 | 用户价值 + 风险 + 可行性 |
| 产出 | 通用能力清单 ← 你看到的那张 | 场景切片清单 |

两种排法都有用，但**不能混在一张表里**。上次你给的标准（亮点/难度前置）本身就是"学习路径"的标准，
所以我给出的也就必然是通用能力列表 —— 这不是排序错了，是**维度选错了**。

## 三、复用度矩阵（把能力摊到场景上）

🟢 换知识库即可　🟡 改配置或加字段　🔴 要重做

| 能力层 | 制度问答 | 坐席 / 柜面辅助 | 信贷 / 授信尽调 | 合规 / 反洗钱 |
|---|---|---|---|---|
| 文档解析入库 | 🟢 | 🟢（几乎不入库） | 🔴 扫描件 OCR、财报表格、合同 | 🟡 |
| 切分与元数据 | 🟢 | 🟢 | 🔴 按报告期、按报表结构 | 🟡 |
| **向量检索** | 🟢 | 🟢 | 🟢 | 🟢 |
| **权限门禁** | 🟢 组织层级 | 🔴 按"客户本人" | 🔴 按"客户归属" | 🟡 按条线 |
| **时效语义** | 🟢 生效/废止 | 🔴 实时值走工具 | 🔴 报告期 | 🟡 案发时点 |
| 动作层（写操作） | — 无 | 🟡 查费率 | 🟡 生成报告草稿 | 🔴 提交可疑交易报告 |
| 输出校验 | 🟢 数字一致性 | 🟢 + 话术禁词 | 🟡 财务勾稽关系 | 🔴 极严 |
| **审计留痕** | 🟢 | 🟢 | 🟢 | 🟡 更严、要防篡改 |
| 评测集 | 🟡 | 🟡 | 🔴 需业务专家标注 | 🔴 需业务专家标注 |

**看懂这张表只需要一句**：绿色的加起来是"平台内核"，红色的才是"这个场景真正的活"。
而红色格子的分布说明 —— **越往高风险场景走，可复用的比例越低**。

## 四、最有力的证据就在你自己的代码里

这个项目**已经是一个"制度问答场景"的特化实现**，不是通用平台。看三处就明白：

| 代码 | 它隐含的场景假设 | 换场景会怎样 |
|---|---|---|
| `RetrievalAdvisor.passesGate` | 权限 = `kb_id` + `doc_level` + `org_codes`（**组织层级**维度） | 信贷要按**客户归属**授权（客户经理只能看自己的客户），`org_codes` 直接失效。而权限维度会**贯穿入库、检索、工具、审计四层** —— 这是牵一发动全身的改动 |
| `TemporalGate` | 时效 = `effective_from` / `effective_until`（生效 / 废止） | 信贷是**报告期**（2024 年报 vs 2025 半年报），反洗钱是**案发时点**，语义完全不同，字段也得换 |
| `CodeRedactor` + `is_code` | 存在"代码类"这种特殊内容 | 只有运维/研发知识库有，制度问答里根本不存在这个概念 |

所以你现在的状态是：**已经选定了"制度问答"这个场景，并在为它做特化 —— 这是对的**。
"一套打天下"不成立，但"一套内核 + 每场景一套策略"成立。

## 五、工具层（Function Calling / MCP）也是同一个分法

- **MCP 是机制**：工具怎么被发现、怎么调用、怎么鉴权 → 可复用
- **工具本身是策略**：`query_fee_schedule` 属于坐席，`check_sanctions` 属于反洗钱 → 每场景一套

MCP 的价值是"接第 N 个系统时不用重写适配"，
但**接哪些系统、暴露哪些工具、给哪个角色用**，全是场景决策 —— 工具权限矩阵没法套用。

## 六、把 P1/P2 的能力"锚"回具体场景

上一张表之所以显得抽象，是因为只写了能力名。把它们贴回制度问答 / 坐席的真实问题，就具体了：

| 能力 | 锚定后的真实问题 | 怎么做 |
|---|---|---|
| **数字一致性校验** | 用户问"跨行转账手续费多少"，答案写 **0.5%**，而原文是 **0.5‰** —— 差 10 倍。或者答案说"5 个工作日到账"，原文是"T+1" | 抽取答案中的数字+单位 → 回检索到的 chunk 原文里找 → 找不到或单位对不上 → 告警/拒答 |
| **轻量制度引用图谱** | ① "《XX 管理办法》废止了，它引用的《YY 规定》还有效吗？业务还能办吗？"② 新手："这个业务一共涉及哪几份制度？"③ 制度管理员："这份制度要废止，影响哪些业务流程？" | 正则抽 `《…》（文号）` 建 A→B 的边；检索 A 时按图展开一跳召回 B、C |
| **Function Calling** | 坐席被问"跨行转账 5 万，手续费多少？几天到？" —— **RAG 答不了**（费率每天变、按客户等级分档）。RAG 能答的是"跨行转账需要什么材料、有什么限额规定" | `query_fee_schedule(bizType, tier, amount)` 走工具；制度类问题走检索。两者在同一个回答里合并 |
| **MCP** | "接入哪个系统"是场景决策：坐席要接**费率中心 + 客户信息系统**；反洗钱要接**制裁名单 + 交易明细系统** | MCP 只负责"接进来不用重写适配"，接谁、给谁用仍是场景决策 |

**看出规律了吗**：每个能力的"机制"部分我一次写完就能复用，
但**它锚在哪个业务问题上、用哪些字段、什么算错** —— 全是场景说了算。

## 七、判断一个新能力能不能套用：三个问题

这套判据可以直接迁移到别的项目上：

| 问题 | 可复用 | 不可复用 |
|---|---|---|
| ① 输入是"文本"还是"业务对象"？ | 文本（文档、chunk、prompt） | 业务对象（客户、账户、交易、额度） |
| ② "正确"由谁定义？ | 通用标准（引用能对齐、审计能追溯） | 业务规则（什么算授权、什么算过期、什么算合规） |
| ③ 出错后果是"答得不好"还是"违规/资损"？ | 答得不好 | 违规、资金损失、监管问责 |

三个问题里有任意一个是"不可复用"，这个能力就必须**重新设计 + 单独评审**，不能靠配置切换。

## 八、这对路线选择意味着什么

**路线 A：横向铺能力**（就是上次那张表）
- 学得广，每个能力都懂原理
- 但每个都是半成品，简历上只能写"了解"
- 适合：面试前突击补知识面

**路线 B：纵向打通一个场景** ← 建议这条
- 选定"制度问答"，端到端做到底，每一层都贴着一个真实问题：

| 层 | 它回答的真实问题 | 状态 |
|---|---|---|
| 1 入库版本管理 | 同一份制度有三个版本，哪版是现行的？ | 待做 |
| 2 检索 | 员工用口语问，制度用条文写，怎么对上？ | 部分（缺 hybrid） |
| 3 权限 | 风险条线能看授信细则，柜员不行 | ✅ 已有三把锁 |
| 4 时效 | 这份制度上个月废止了 | ✅ 已实现 |
| 5 引用 | 答案要能指回第 X 条 | ✅ 已实现 |
| 6 数字一致性 | 答案说的比例和原文对不上 | 待做 |
| 7 引用图谱 | A 废止了，它引用的 B 还有效吗 | 待做 |
| 8 审计 | 三个月前那个回答是怎么来的 | 待做 |
| 9 评测 | 改了 prompt 之后是变好还是变坏 | 待做 |

**建议走 B，把 A 的能力当成 B 路上的顺带。** 理由很实在：
面试官问"你做过什么"时——

- ❌ "我了解 hybrid 检索、MCP、GraphRAG、rerank"（听起来像读过文档）
- ✅ "我做过一个制度问答系统，端到端跑通了入库版本管理、权限、时效、引用、数字校验、审计，
   其中踩了 X/Y/Z 三个坑"（听起来像做过事）

**端到端跑通一个场景，比横向了解八个能力，在"当工作经验用"这个目标上价值高得多。**

## 九、一句话总结

> **能套用的是管道，不能套用的是语义。**
> 你手上这套代码已经证明了这个结论 —— 它不是一个通用平台，
> 而是一个**"制度问答场景"的特化实现**，而且这个选择是对的。
> 接下来该做的不是继续横向加能力，而是把这个场景**纵向打通、做深、做完整**。
